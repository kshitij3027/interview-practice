# ServiceClock — 60-minute AI-assisted full-stack interview

## Context
ServiceClock is a working service-operations console for a company maintaining cold-storage equipment at customer facilities. Dispatchers look up work orders, inspect service notes and track the latest disposition. They must honor contractual service-level clocks, which run only during each site's working hours and stop while a technician is waiting for the customer.

## Existing behavior (already implemented)
The starter is a dependency-free **Python 3.11+ HTTP backend** with fixture-backed in-memory state, a **vanilla JavaScript browser frontend**, and working automated tests. Select a customer account, search work orders, filter by status, view a work order and its site, and edit an internal note. List results are sorted by work-order ID with `total` counted before `limit`; notes are trimmed, no-op edits do not alter revisions, and stale writes return 409. The browser ignores outdated list/detail responses when the selection changes. The seed data resets at server restart. Preserve all of this behavior.

## Supplied data
- `fixtures/workspace.json` contains customer accounts, service sites with **IANA time zones**, weekday business hours and local-date holidays, priority SLAs, and 12 work orders with their current state, revision and notes.
- `fixtures/activity.jsonl` contains historical work-order state changes. The partner's activity feed can arrive out of timestamp order, be redelivered, and contain conflicting or invalid records. These are **historical** records, not a completed SLA engine. Pay attention to the distinction between an activity's effective time and its ingestion time.
- `server/`, `public/`, and `tests/` hold an already-running work-order directory with note editing. The requested SLA calculation and state-transition features are intentionally absent.

## Customer/business problem
A dispatcher needs to tell a client how much contractual response time remains on a work order. A customer-waiting period must not consume service time; nights, weekends, site holidays and local time changes must not either. Dispatchers also need to pause, resume or resolve work **without losing an update from another operator**. A request might succeed but its response might be lost, so repeating an operation must not create a second state change. Manual notes remain editable and must participate in the same revision checks.

## Primary feature request
**Add one end-to-end, server-authoritative SLA clock and work-order state-transition workflow.** Show the as-of SLA calculation on a selected work order, allow supported pause/resume/resolve actions, surface conflicts and safe retries, and refresh list/detail/SLA data without a page reload. Implement backend semantics, HTTP endpoints, browser interactions, and focused tests.

## Acceptance criteria (observable behavior)
1. Add `GET /api/jobs/:id/sla?account=<accountId>&asOf=<instant>` returning `{jobId,asOf,budgetMinutes,chargedMinutes,remainingMinutes,overdueMinutes,state,paused,dueAt,resolvedAt}`. All counts here are **integer whole minutes**, not rounded floating-point hours. `asOf` is an offset-aware ISO-8601 instant at minute precision; default to the current UTC server minute when omitted. Unknown/cross-account jobs return 404; invalid `asOf` or an `asOf` before job opening returns a structured 400.
2. SLA budgets come from the priority mapping in `workspace.json`. Compute charged minutes between `openedAt` and `asOf` only when a work order is `in_progress` and the site is inside its local weekly business calendar. Each site's working days and opening/closing wall-clock times, plus the site's closed local holiday dates, are authoritative. The business interval is **half-open** `[open,close)`; touching the closing time does not add a minute. Skip weekends and holidays. Use real IANA timezone rules, including daylight-saving shifts; do not assume all sites are in Pacific Time or a fixed UTC offset.
3. Historical events use `eventId`, `jobId`, `occurredAt`, `receivedAt`, and `state`. Event ID is an idempotency identity: identical payloads may appear repeatedly and count once. When the same ID claims conflicting canonical content, that ID is untrustworthy and must not change any work order. Invalid events must not break unrelated work orders. The canonical history is ordered by **effective** `occurredAt`, then lexicographically by event ID (not receipt order); a same-instant later event in this order determines the state after that instant. Job opening starts in `in_progress`, unless an authoritative event at opening changes it. Events after `asOf` must not influence the requested result. Only `in_progress`, `waiting_customer`, and `resolved` are valid states; `resolved` is terminal. Document how you handle contradictory state transitions in history rather than silently double-charging or restarting the clock.
4. Waiting-customer periods stop the SLA clock, including those that span holidays or nonworking hours; resuming restarts it without charging the pause interval. Resolution stops the clock permanently. Return `resolvedAt` when the job is resolved as of the requested instant. `state` is `on_track`, `paused`, `breached`, `met`, or `missed`: a still-open work order with `chargedMinutes >= budgetMinutes` is `breached` even when currently paused; an unresolved waiting order below budget is `paused`; a resolved job is `met` if its consumed minutes at resolution are <= budget and `missed` otherwise. `remainingMinutes=max(0,budget-charged)` and `overdueMinutes=max(0,charged-budget)`.
5. `dueAt` is the exact first service-calendar instant at which the budget would be exhausted if the work order continued **without future pauses** from the requested `asOf`, incorporating any historical pauses. If already exhausted, return the actual deadline instant from historical elapsed work, not `asOf`; for a resolved job return the actual deadline if the budget was exhausted before resolution, otherwise `null` because no deadline was reached. For an unresolved waiting job with time still remaining, use `null` (the resume time is unknown). Serialize instants as UTC ISO-8601 strings ending in `Z`. Explain any reasonable approximation you make for unusual site calendar transitions.
6. Add `POST /api/jobs/:id/transitions?account=<accountId>` accepting `{to,expectedRevision,requestKey}`. Valid `to` values are `waiting_customer` (only from `in_progress`), `in_progress` (only from `waiting_customer`), and `resolved` (from either open state). A resolved work order cannot reopen. The server, **not the browser**, stamps transition `occurredAt` using its current clock and rejects transitions that would precede the last authoritative historical event. Successful transitions append exactly one activity, change status, increment that work-order revision and the dataset revision **once**, and return an immutable receipt with transition ID, applied timestamp, updated work order and SLA snapshot. Reject malformed input (400), hidden/unknown work order (404), stale revision or illegal transition (409) with `{error:{code,message}}`.
7. A trimmed `requestKey` of 8–64 characters is scoped per account and identifies the complete transition intent `(account,jobId,to,expectedRevision)`. A successful same-key/same-intent retry returns the **original receipt** unchanged, even if notes or subsequent transitions have occurred. Same key with different intent returns 409 `KEY_CONFLICT`. A rejected attempt does not reserve a key. At most one mutation can win when requests arrive together: the revision precondition and state transition are atomic. Check a known successful retry **before** rejecting a now-stale revision.
8. The browser must show SLA status, consumed/remaining minutes and deadline (or why no deadline is available). Add pause/resume/resolve controls and a readable pending/success/failure state. On uncertain transport failures, preserve the operation's request key and intent for safe retry, not a new key. On 409 preserve the selection, show the conflict and refresh authoritative details before an intentional new attempt. Old results from previous account/job selections must never overwrite the current screen. An existing note edit should make a pending transition with an older revision stale.
9. The fixture is small, but production may have **100,000 jobs, 500,000 activity records and repeated SLA reads**. Avoid scanning all jobs or a minute at a time through years of history for each request. Bound raw input sizes; validate timestamps and time zones; avoid quadratic reprocessing of redelivered events. Give time/space complexity estimates in your walkthrough.
10. Add focused tests for out-of-order and duplicate events, conflicting IDs, business opening/closing boundaries, holidays, a pause across a weekend, daylight-saving changes, same-instant events, resolving before/after deadline, account isolation, stale notes, key replays/collisions, concurrency, and existing list/note behavior. Do not remove or weaken current passing tests.

## Constraints
Keep Python 3.11+ standard library, the fixture-backed single-process store, and plain browser JavaScript. No database, Redis, external calendar API, task queue, authentication service, or additional dependencies. Use integer minutes and offset-aware UTC timestamps. You may adjust server routes, store structure, shared types and frontend state. The baseline app need not show the new clock or transitions until you implement them.

## Deliverable and scope
A working vertical slice across domain calculation, HTTP, UI and tests; a brief explanation of correctness, performance, failure recovery and choices. Out of scope: persistence across restarts, true multi-process coordination, public holidays beyond supplied site dates, service staffing schedules, time-zone editing, billed labor hours, and a redesign of the existing directory.

## Setup / build / test / run
Requires Python 3.11+ and a modern browser; optional Node.js enables JavaScript syntax checks. No pip or npm dependencies.

```bash
./scripts/build.sh
./scripts/test.sh
./scripts/verify.sh
./scripts/run.sh
```

Open `http://127.0.0.1:8080`. Set `PORT=8081` to choose another port. The starter build/tests/fixture verification are expected to be green **before** you add the requested capability; they do not encode the full feature acceptance criteria.

## Explicit 60-minute AI-assisted interview instruction
You have **60 minutes**, using Claude Code, Codex, ChatGPT or similar tools if helpful. First inspect the working application, existing API, fixture records and behavior tests. Decide what to build and verify first; work incrementally and explain complexity, failure scenarios and remaining gaps in a walkthrough. One-shot generated code that handles only ordinary working hours and the happy-path action will not satisfy this exercise.
