# BatchGuard — HARD 60-minute AI-assisted full-stack interview

## Context
BatchGuard is a quality-control console for a manufacturer with multiple plants. Operators review production lots, supplier specifications and measurements from instrument exports. An instrument can resend the same observation after a network interruption, and it can issue corrected measurements later. Manual re-entry is slow and makes lot-readiness decisions difficult to audit.

## Existing behavior (already implemented)
This is a functioning **Python 3.11+ FastAPI service with an in-memory fixture-backed store and dependency-free browser JavaScript**. The application lists 12 lots, supports plant/status filtering and search, opens lot details with the applicable specification and previously recorded samples, and allows editing an internal note. List results are sorted by lot ID, and `total` is calculated before `limit`. A changed, trimmed note increments that lot's revision and the dataset revision exactly once; a no-op does not. A stale note edit returns 409. Late list/detail responses cannot replace a newer selection. **Do not break these behaviors.** Restarting resets the seed data.

## Supplied data
- `fixtures/workspace.json`: three plants, three product specifications, 12 lots (both open and closed), current lot revisions, existing notes and four previously accepted samples. Each specification declares an inclusive pH range, an inclusive *upper* moisture percentage and the minimum number of distinct samples required to judge a lot ready.
- `fixtures/instrument_export.csv`: a representative instrument report with repeated event IDs, corrected samples, out-of-order revisions, varying moisture units, malformed values, samples for closed lots, and a conflicting equal-revision sample. CSV quoting and input order matter.
- `app/store.py`, `app/api.py`, `public/`: working domain state, API and browser screens. The requested import behavior is **not** present.

## Customer/business problem
The plant analyst receives a mixed CSV export for several lots. They want to import trustworthy readings once, see which individual samples were accepted or rejected, and immediately understand each lot's QC readiness. Another operator can edit a lot while the file is open; a network timeout can happen *after* the import succeeds. The analyst must be able to retry without duplicating samples or silently overwriting newer work. One bad sample or stale lot should not discard valid samples from other lots.

## Primary feature request
**Add one end-to-end instrument sample intake and lot-readiness workflow.** Let an analyst choose or paste a CSV report, submit it to the server, inspect per-lot and per-sample outcomes, and see updated readiness across both the list and selected lot detail. Build the domain rules, HTTP contract, browser interactions, and focused verification. Do not add a separate approval/publishing stage.

## Acceptance criteria — observable behavior
1. Add `POST /api/intakes` receiving JSON `{csvText,requestKey,expectedRevisions}`. `csvText` is the complete CSV text; `requestKey` is a trimmed 8–64-character string; `expectedRevisions` maps every **referenced lot ID** to the lot revision the analyst observed (nonnegative integers). Required exact CSV header names are `event_id,lot_id,sample_id,sample_revision,ph,moisture,moisture_unit`; accept their order in any permutation and UTF-8 BOM. Respond with a reusable receipt including `requestKey`, `results` and `datasetRevision`. Each `results` entry has `lotId`, `status` (`applied`, `unchanged`, `rejected`), sorted `acceptedSampleIds`, sorted `rejectedSamples` with stable error codes, authoritative `revision` if known, and the resulting `quality` if known. Sort results by lot ID. Return structured HTTP 400 for invalid request envelopes or CSV headers and 409 for a request-key collision. Bad individual rows must be reported rather than silently dropped.
2. An instrument row describes a complete sample with `event_id,lot_id,sample_id,sample_revision,ph,moisture,moisture_unit`. A sample identity is `(lot_id,sample_id)`. IDs are case-sensitive and must be nonempty after trimming. `sample_revision` must be a positive integer. Use exact decimal arithmetic; reject NaN, infinity, booleans and invalid numeric strings. pH must be within `[0,14]`. Moisture units are exactly `pct` and `fraction`; normalize to percentage (`fraction * 100`), with values in `[0,100]` percent. Do not round values before comparison. A source sample with invalid data must not be persisted.
3. Repeated delivery of the **same `event_id` with identical normalized row content** is one observation; if one `event_id` claims different contents, reject every implicated sample and do not allow one input order to win. For the same `(lot_id,sample_id)` within a report, the greatest `sample_revision` is authoritative regardless of CSV order. Distinct content at the same greatest revision is ambiguous: reject the sample. For a sample already stored, an older revision must not overwrite it; an identical revision and identical normalized readings is a no-op; an identical revision with different content is a conflict. Newer valid corrections replace the stored sample. A retry must never duplicate samples.
4. Process valid independent samples even when other samples are invalid, but apply or skip each **lot** according to its revision precondition. An unknown or closed lot, a missing/mismatched expected lot revision, or a malformed sample must be reported with explicit stable reasons. Reject the affected lot on stale/closed/unknown conditions, leaving its samples unchanged, without preventing other lots from succeeding. A malformed sample must not block other valid samples in the same eligible lot. Do not advance any revision for rejected/no-op changes. When one or more samples materially change a lot, increment its revision **once per intake**, and increment the dataset revision **once per changed lot**.
5. Compute `quality` for every lot from its **currently stored distinct samples** and its own product specification. Return `{state,sampleCount,failedSampleIds}` where `failedSampleIds` are sorted sample IDs violating at least one specification limit. `state` is `fail` whenever any sample fails, otherwise `pass` when `sampleCount >= minSamples`, otherwise `pending`. pH and moisture thresholds are inclusive. A corrected sample must replace—not double-count—the earlier reading. Expose the same authoritative quality information in `GET /api/lots` entries and `GET /api/lots/:id` details; existing filtering and note editing must still work.
6. `requestKey` identifies the **complete intake request** (CSV contents and expected revisions, not JSON property ordering). Repeating an already successful request with the same key returns the original immutable receipt, including original revisions/outcomes, even if other users have since edited the lots. Reusing a key with different contents is a 409 `KEY_CONFLICT`; simultaneous same-key requests must not apply twice. A transport failure must not be treated as proof of failure by the browser.
7. The UI needs a file picker and a paste option, a clear submit action, a readable results table with accepted/rejected sample reasons, and lot-readiness badges or counts for both list and detail. Show request/in-progress/failure state. If a response is lost, retain the exact file and request key for safe retry. On a stale-lot conflict, show the rejected lots and allow refreshing current revisions before a *new* attempt. Ignore results from earlier submissions after the user changes the selected input. Never claim success based only on client-side calculations.
8. Enforce a **256 KiB UTF-8 CSV limit and 2,500 physical data rows** per request (excluding the header). Reject invalid UTF-8/oversized input and incorrect CSV structure with a structured 400 before changing anything. Keep response ordering deterministic and avoid a per-row scan of every previously stored sample. A production installation may manage 50,000 lots and millions of stored samples; the fixture is compact but the solution should justify time and memory costs.
9. Test at least an ordinary import, a corrected sample, wrong/equal revisions, mixed valid and invalid rows, a closed or stale lot mixed with a valid lot, inclusive boundaries and fraction conversion, retry replay and request-key conflict. Preserve the existing green tests and working console.

## Constraints and out of scope
Keep the current FastAPI backend, in-process state and browser UI. No database, authentication, external instruments, cloud service, background worker, persistent storage, exports, or actual physical lot release is necessary. An import changes **measurement records and displayed QC readiness**, not the lot's `open`/`closed` lifecycle. The route may return one receipt synchronously. HTTP errors have shape `{error:{code,message}}`; failures unrelated to individual samples should change nothing. Avoid introducing a third-party CSV parser if the Python standard library suffices. Do not implement unrelated features.

## Setup and commands
```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
./scripts/build.sh
./scripts/test.sh
./scripts/verify.sh
./scripts/run.sh
```
Open **http://127.0.0.1:8080**. Read the fixtures and the existing routes before editing. The first three commands after installation are expected to pass on the unmodified starter. The missing intake endpoint is an exercise requirement, not a baseline failure.
