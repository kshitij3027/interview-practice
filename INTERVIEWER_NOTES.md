# POST-PRACTICE ONLY — Interviewer Notes

Do not read this file before completing the 60-minute exercise.

## Intended solution outline

A strong solution adds explicit action-item mutation methods in the store/service layer, with normalized create payloads and a server-side request-key registry for successful creates. Permanent IDs are generated by the server; retries return the original result without repeating revision increments. Toggling checks the action's own revision before mutation and returns current server state on conflict.

On the client, optimistic rows need a client-local identity distinct from the eventual server ID. Creation should insert a pending row immediately, retain the logical request key for retry, and reconcile that exact row when the response arrives. Toggle should optimistically change one row, mark only that row in-flight, and replace/rollback from authoritative server state on failure. Mutation completion must be guarded by the incident context that initiated it so old responses cannot paint onto a different selected incident.

A compact implementation can keep the existing single global store, but it should track action filters/search plus pending create/toggle metadata explicitly enough that rendering is derived rather than patched ad hoc.

## Subtle traps / hidden checks

- Normalize create payload before storing/comparing idempotency fingerprints; `"  Fix cache  "` and `"Fix cache"` should not become different logical payloads if the accepted normalized fields are otherwise equal.
- Empty owner should normalize consistently to `null`/unassigned before idempotency comparison.
- Invalid create attempts should not reserve a request key as a successful idempotent result.
- Same request key + same successful payload returns the original item/result and does not advance action, incident, or dataset revisions again.
- Same request key + materially different payload must be rejected rather than treated as a retry.
- A stale toggle must perform zero mutation; returning the current action or incident snapshot makes client recovery straightforward.
- Parent incident revision changes on action mutations, so the existing severity editor can legitimately become stale after action work. Do not bypass its concurrency rule to make this disappear.
- The action's own revision increments only on successful status change; creating unrelated items should not increment every existing action revision.
- The optimistic open→done transition under an `open` filter should hide immediately. If the request fails stale, authoritative rollback should naturally make it visible again.
- A delayed mutation for incident A can complete on the server after the user selects incident B. It should not mutate B's visible client state. A later revisit/fetch of A should still show the server mutation if it actually succeeded.
- Request delay should be bounded and applied before the mutation response path in a way that allows deterministic local race testing without changing business semantics.
- Sorting should be server-deterministic after reconciliation; temporary optimistic rows may need a stable local fallback while pending.

## Expected prioritization

1. Preserve baseline and understand revision/list/detail flow.
2. Implement backend create validation, IDs, revision accounting, and idempotency with focused tests.
3. Implement stale-safe toggle backend behavior and tests.
4. Add minimal optimistic UI for create and toggle.
5. Add filters/search plus correct rollback/reconciliation.
6. Exercise delayed incident-switch and stale-toggle scenarios; polish last.

A candidate who spends most of the hour styling or building abstractions before securing idempotency/revision semantics is mis-prioritizing the interview.

## Likely failure modes

- Using the temporary browser ID as the permanent server ID.
- Generating a new request key on retry, defeating create idempotency.
- Storing idempotency only after the response reaches the browser rather than after the server mutation succeeds.
- Blindly replacing the currently selected incident when any delayed response finishes.
- Refetching the whole page after every mutation and losing filters/search/drafts.
- Applying optimistic toggle locally but never rolling back/reconciling on 409.
- Using the parent incident revision instead of the action revision for toggle concurrency, or failing to increment the parent/global revisions after action mutation.
- Disabling the entire action board while one row toggles instead of isolating row-level in-flight state.
- Updating open-action counts only in the detail panel and leaving list summaries stale.
- Duplicating pending and reconciled rows when create responses arrive.

## What to inspect after the hour

- Is create idempotency truly server-side and keyed to normalized logical payload?
- Can a stale toggle mutate anything?
- Are revision increments exactly once per successful logical mutation?
- Does the client model pending identity explicitly enough to avoid duplicate rows?
- What happens to an optimistic row under `open`/`done` filters on success and failure?
- Can a response for a no-longer-selected incident corrupt current UI state?
- Does the existing severity update still reject stale revisions correctly after action mutations?
- Did the candidate add targeted tests for the dangerous semantics and actually run delayed/conflict scenarios?
