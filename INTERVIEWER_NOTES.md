# POST-PRACTICE ONLY — ReviewDesk interviewer notes

## Intended structure

A capacitated bipartite matching problem, separable by queue. Documents have demand one; reviewers have integer capacities. The ordered coverage objective is lexicographic over a Boolean vector, not a weighted priority sum. The set of matchable documents is a transversal matroid: conceptually replace each reviewer by capacity-many identical slots (only for proof; not necessary in code). Thus a greedy independence test in descending priority/ascending ID order yields the lexicographically greatest basis, and every basis has maximum size.

A strong implementation processes documents in that order. Keep reviewer occupancy lists, and for each document search for an alternating augmenting path from it through eligible reviewers and their currently assigned documents to a reviewer with spare capacity. A full reviewer may require moving one of its assigned documents, which can in turn displace another. Only commit moves on a successful path (e.g., DFS unwinding or reconstructed BFS path). Reset visited state per attempted insertion, not per branch of recursive search. The previous matched documents remain matched if insertion succeeds; failed insertions leave the assignment unchanged. Existence of an augmenting path is exactly the test for whether the current covered set plus this document can be matched. By the matroid exchange property a rejected document cannot become independently addable later and any independent set extends to a maximum basis; therefore this priority order is globally optimal under both objectives. A useful explanation without matroid vocabulary: maintain maximum matching on every prefix; each newly added document either increases prefix rank by one or cannot be included while keeping the earlier chosen documents, and the lexicographically best basis consists of precisely those rank increases.

Use direct reviewer capacity and occupant lists, sorted candidate options and deterministic occupant traversal; avoid localeCompare unless explicitly configured to reproduce ASCII order. Default string sort on these ASCII IDs suffices. Visit each reviewer at most once in one search (after reaching it, all relevant occupants can be explored); document visit tracking can also be used. Do not remove occupants before knowing that the whole search succeeds. A failed branch must not consume capacity. Use Map rather than unsafe object keys because IDs such as __proto__ are valid. Each plan invocation owns all assignment state. Sort output arrays by document ID, not priority or arrival order.

For queue q with Dq documents, Rq reviewers and Eq eligibility links, a direct search costs O(Eq + Dq + Rq) per attempt if visited markers prevent repeated exploration, so total O(sum Dq*(Eq+Dq+Rq)) plus sorting O(D log D). Memory O(E+D+R), recursion depth at most O(Rq) with reviewer visitation. With Dq<=300, Rq<=100 and at most 20 links per document, the bounded queue sizes make this credible. Measure a high-overlap dataset, not just random easy cases. A capacity-slot expansion can multiply eligibility edges by capacity, especially with quotas that dwarf demand; it may still be defensible if tightly bounded and measured. Flow networks with incremental augmentation in priority order are equally valid. Another exact alternative fixes each coverage decision using a feasibility solver while preserving maximum coverage; likely slower but potentially viable with partitioning and careful reuse. Scalar costs based on priority sum are wrong; exponential lexicographic weights require exact arbitrary precision and a credible performance story. AI or heuristics may generate a proposal but require exact checks for optimality, not merely feasibility.

## Hidden checks and traps

- First-fit trap: reviewer A and B capacity one; high-priority doc X eligible A/B, lower Y eligible only A. Both must be covered, X→B, Y→A. A chain X(A/B), Y(B/C), Z(A) with three unit quotas requires a longer rearrangement from a first-fit start.
- Capacity >1: R has capacity 2 and occupants X (R/S) and Y (R-only); Z (R-only) must displace X to S, not Y. Reverse occupant ordering to ensure both alternatives are explored.
- Priority preference: three documents with only R (capacity one), priorities 4,5,5, IDs A,Z,B respectively. Cover B, not Z or A. Check ASCII uppercase/lowercase/underscore differences and output sorting.
- Hall-type bottleneck: abundant total capacity in reviewers irrelevant to constrained documents; no invalid assignments to fill target count. Generate small random cases and enumerate all feasible subsets/assignments as an oracle; compare rank and full lexicographic coverage vector, not just total priority.
- Failed insertion after exploring multiple occupied reviewers must preserve earlier allocations and permit later independent documents. Empty options, zero quotas, empty catalog, and queues without reviewers must work.
- Reverse both catalog arrays and each eligible list, add exact duplicates, rerun; output must be identical. Test repeated plan calls on frozen/unchanged normalized input and unusual valid IDs. Conflicting duplicates and cross-queue options must continue to fail before any stdout.
- Stress: 100 queues × 300 docs, each with 100 reviewers and up to 20 choices. Mix saturated queues (small quotas, heavy overlap, many failed searches) with mostly unused quota-300 reviewers. Measure under the declared heap budget, ensure no cross-queue work and validate output. Run node --max-old-space-size=256 cli.mjs generated.json; report machine and wall time rather than claiming universal timing. No performance claims without measurements.

## AI-agent failure modes

Common generated solutions sort by priority then greedily choose the reviewer with most capacity, maximize a scalar weighted score instead of the ordered covered vector, perform a separate global optimization per priority without preserving earlier coverage, reset visited state in recursive calls (blowup), mutate occupancy on a failed search, or use a giant expanded matrix. Some solutions assign each reviewer only one document, confuse eligible with assigned, or silently deduplicate conflicting IDs. Ask for a concrete counterexample to their initial design and verify that the code handles it. Test correctness before chasing micro-optimizations.

## Suggested one-hour prioritization

0–8 min inspect data, clarify objective and write a tiny counterexample. 8–30 min implement exact coverage and valid witness. 30–42 min deterministic ordering and edge cases. 42–52 min targeted tests plus randomized oracle or scale sample. 52–60 min run baseline, demonstrate output and explain proof, complexity and remaining gaps. Inspect search ownership, how capacity is restored on failure, queue isolation, deterministic iteration, handling of duplicate records, complexity under saturated queues, and whether test assertions independently check the objective. Credit transparent partial solutions, but apply rubric caps when exactness or scale is unaddressed.
