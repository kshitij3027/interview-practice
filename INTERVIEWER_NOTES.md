# INTERVIEWER NOTES — POST-PRACTICE ONLY

## Intent
This is schema evolution across a live form, not generic CRUD. The candidate should discover that template versions are unsorted, IDs persist through labels and ordering, and a direct upgrade can skip versions. The server is the source of truth; the browser previews and commits a reviewed revision, not an arbitrary answer map.

## Strong implementation outline
- Read relevant inspection/template under existing state lock. Identify maximum numeric version. Reject non-draft and current-version records.
- Create a pure preview calculation shared by GET and POST: index target fields by ID, traverse the source fields in order, distinguish key presence from truthiness, retain only same type and validAnswer(target,value), and produce exactly one reason per discarded value. Determine missing required IDs by traversing target order, including trimmed blank text. Keep valid blank text as an answer while reporting it missing for required completion. Do not consult the archive when finding active answers.
- POST validates integer revision and target, then checks current state and reuses preview logic within one withState(true, ...) callback. Only after validation update answers, version, archive and revision. Existing store lock covers read/derive/write; splitting preview and mutation across state calls is unsafe. Append archive records, never rewrite historical ones. Return authoritative detail (with pinned fields) and useful upgrade information. Reject replay rather than double-append; a new request can refresh and see the committed state.
- Browser adds preview state tied to selected ID/generation/revision. Render via textContent, not HTML interpolation of fixture or user data. Confirm only current preview, disable while pending, clear preview on edit/select, ignore late GET/POST responses, refresh after uncertain result or conflict. Offer a fresh preview rather than blindly retrying stale state.
- Complexity: O(V + Fsrc + Fdst + A) time for preview (V versions, fields and answers) with O(Fdst + A) auxiliary space. Reuse existing field lookup/validator. JSON file read/write remains O(total fixture size), acceptable under local constraints. Alternative indexed or two-pass pure functions are acceptable.

## AI-agent failure modes and traps
Array order used for latest, version-by-version migration inadvertently drops answers that survive direct upgrade, using empty()/truthiness, coercing types, restoring from archive, matching labels, relying on source validator instead of target, silently deleting discarded answers, failing to validate stale target, optimistic client mutation, double archive on retries, conflicting domain and UI rules, stale response affecting a different inspection. Watch PHP strict comparisons and null semantics. Existing answer endpoint must still use pinned version and distinguish false/zero from absent.

## Recommended prioritization
0–8 min inspect fixture, UI, state and routes; 8–25 min pure preview and focused tests; 25–38 min locked apply/API and conflict test; 38–53 min UI workflow with refresh; 53–60 min run build/test/verify, demo and explain gaps. Partial credit favors a correct vertical slice over styling.

## Walkthrough
Ask the candidate to show I-101 preview and resulting archive, I-102's zero/false and prior archive, stale preview in two tabs, invalid target without mutation, post-upgrade editing, and baseline tests. Inspect actual persisted state and API error paths. Ask why candidate chose direct migration, what guarantees atomicity, how they handle a lost response, what happens if a label changes or field comes back, and which production storage/auth changes would be necessary.
